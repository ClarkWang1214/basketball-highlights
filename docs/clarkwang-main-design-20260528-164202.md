## Problem Statement

打篮球半场3V3时，用三脚架+手机录制整场比赛，赛后需要手动用剪辑软件找出进球瞬间并剪辑成集锦——这个过程耗时且枯燥。想要利用多模态 AI 自动完成"从比赛视频中识别进球时刻 → 剪辑拼接 → 输出集锦"的完整流程。

核心诉求：**学习如何用 vibe coding 的方式把整个流程搭建起来**，初版做最小可用版本，后续迭代。

## What Makes This Cool

- 自己造一个"私人篮球集锦剪辑师"——打完球就有集锦看
- 把 Mimo v2.5 视频理解能力应用到真实场景，从 API 调用到视频处理全链路打通
- 后续可以扩展到实时录制+边录边剪、球员数据统计、多角度融合

## Constraints

- **学习优先**：代码可以不够完美，但流程要完整跑通
- **成本可控**：Mimo v2.5 按量计费，只在关键时刻调用 API，大部分工作用 CV 搞定
- **初版做减法**：输入 mp4 → 输出集锦 mp4，命令行搞定，不需要 UI
- **视频来源**：三脚架固定机位拍摄的半场 3V3，镜头相对稳定

## Premises

1. Mimo v2.5 支持直接视频 URL 输入（MP4/MOV，≤300MB，fps 0.1-10，max 2048帧），不需要手动抽帧
2. CV（OpenCV）可以完成运动检测、ROI 区域变化检测等"粗活"，零 API 成本
3. 固定机位意味着篮筐位置相对固定，可以预设 ROI（通过 `--roi x,y,w,h` 命令行参数或配置文件传入）
4. CV 粗筛优先保证高召回（宁可多报不漏报），目标是 80%+ 进球被覆盖，每场产生约 30-60 个候选片段
5. 初版期望：本地 Python 脚本，`python highlight.py input.mp4 -o output.mp4 --roi 640,120,200,300`
6. Mimo v2.5 视频理解 API 的接入方式待 Step 0 验证——优先测试 base64 编码直接传入（与现有 MCP 服务的图片处理模式一致），备选方案为公网 URL

## Approaches Considered

### Approach A: 纯 VLM 路线

直接把整场比赛视频丢给 Mimo v2.5，在 prompt 里要求返回所有进球时间戳。

- **优点**：代码最少（~50行），最接近 vibe coding 体验
- **缺点**：整段视频 token 消耗巨大（一场 30 分钟比赛可能数万 token）；Mimo 能否准确定位多个时间戳待验证；成本不可控
- **风险**：高。如果 Mimo 无法可靠返回时间戳，方案直接失效

### Approach B: CV 粗筛 + VLM 精判（推荐）

OpenCV 检测篮筐区域的运动变化 → 截取候选片段（~10秒）→ Mimo v2.5 逐段确认是否是进球 → ffmpeg 剪辑拼接。

- **优点**：API 调用量可控（每场 ~20-40 次），成本和效果平衡，CV 部分网上资源丰富
- **缺点**：代码量中等（~300-500行），需要处理 CV 边界情况
- **适合学习**：同时接触 CV（OpenCV）和 VLM（Mimo）两个领域

### Approach C: 纯传统 CV 路线

YOLOv8 检测篮筐+球+轨迹，完全本地处理，不依赖 API。

- **优点**：零 API 费用，已有开源项目可直接参考
- **缺点**：需要理解 YOLO/ML 概念，学习曲线陡峭，不算 vibe coding；需要标注数据微调模型才能达到好的效果
- **对于学习项目来说太重了**

## Recommended Approach

**Approach B: CV 粗筛 + VLM 精判**

理由：在 vibe coding 的体验（靠 prompt 解决问题的爽感）和工程实用性（成本可控）之间取得了最佳平衡。同时接触两个技术栈，学习收获最大。

### 整体流程

```
mp4 输入
  │
  ▼
[1] OpenCV 运动检测
  - 计算帧间差分，定位篮筐区域附近的高运动时刻
  - 输出：候选时间戳列表 [t1, t2, t3, ...]
  │
  ▼
[2] 候选片段提取
  - 每个候选时间戳截取 ±5~8 秒视频片段（10-16秒）
  - ffmpeg 精确裁剪，临时保存
  │
  ▼
[3] Mimo v2.5 逐段判定
  - 每个片段发送给 Mimo，prompt："这段篮球视频中是否有进球发生？如果有，进球发生在第几秒？"
  - 收集确认的进球时间戳
  │
  ▼
[4] 集锦生成
  - 每个进球时刻截取 ±4~6 秒（进球前动作 + 进球 + 反应）
  - ffmpeg concat 拼接所有片段
  - 可选：添加简单转场、配乐
  │
  ▼
output.mp4（进球集锦）
```

### 关键模块

| 模块 | 技术选型 | 说明 |
|------|----------|------|
| 视频读写 | OpenCV (cv2) | 读帧、计算帧差、预览 |
| 运动检测 | 帧间差分 + 篮筐 ROI | 固定机位下篮筐位置相对固定，重点关注该区域的运动峰值 |
| 视频裁剪 | ffmpeg (subprocess) | 精确裁剪、拼接，比 OpenCV 更可靠 |
| VLM 判定 | Mimo v2.5 API (OpenAI SDK) | 视频 URL 输入，prompt 工程是关键 |
| 编排逻辑 | Python 主脚本 | 串联所有步骤，命令行参数解析 |

### Mimo API 集成方式（Step 0 必须验证）

这是整个方案的**最关键技术决策点**。现有 `mimo_mcp_server.py` 对图片使用 base64 编码直接传入 OpenAI SDK，视频有两种可能路径：

1. **Base64 编码（优先尝试）**：使用 OpenAI SDK 的 `video_url` 类型，传入 `data:video/mp4;base64,...` 格式。与现有图片 MCP 模式一致，无需外部服务。
2. **公网 URL（备选）**：需要将本地文件上传到可公开访问的地址（OSS、临时文件服务等），增加复杂度。

**Step 0 验证脚本需同时测试两种方式。**

### 成本估算

假设一场 30 分钟半场 3V3（以 fps=2 为例）：
- CV 粗筛产生 ~40 个候选片段
- 每段 ~12 秒，按 fps=2 抽帧约 24 帧，估算每段消耗 ~2000-5000 tokens
- 40 段 × 4000 tokens ≈ 160K tokens
- 按 Mimo v2.5 公开定价，约几块钱人民币一场比赛

### Technical Notes: ffmpeg 命令参考

**精确裁剪（seek + extract）：**
```bash
# -ss 放在 -i 之前 = 快速 seek（关键帧精度），放在之后 = 逐帧解码（精确但慢）
# 初版用快速 seek 即可，±1 秒误差可接受
ffmpeg -ss <start_time> -i input.mp4 -t <duration> -c copy clip_N.mp4

# 如需精确到帧（Step 4 最终集锦）：
ffmpeg -ss <start_time> -i input.mp4 -t <duration> -c:v libx264 -crf 18 -preset fast clip_N.mp4
```

**拼接（concat demuxer）：**
```bash
# clips.txt 内容：file 'clip_1.mp4' / file 'clip_2.mp4' / ...
ffmpeg -f concat -safe 0 -i clips.txt -c copy output.mp4
```

### 运动检测策略

仅用帧间差分 + ROI 阈值会产生大量误报（篮板、传球、突破都会触发）。增加二级特征过滤：

1. **一级：帧间差分** — 计算 ROI 区域帧间变化幅度，超过阈值标记为"运动事件"
2. **二级：时序模式过滤** — 进球通常伴随：高运动（投篮动作）→ 短暂低运动（球飞行）→ 篮网区域再次高运动（球穿过）+ 球员反应（举手、转身）。相邻事件合并为同一候选，间隔 <2 秒的事件视为一个片段
3. **输出**：候选时间戳列表，确保高召回（宁可多报），由 Mimo 做最终精判

### 边界情况处理

| 场景 | 处理方式 |
|------|----------|
| 零进球（CV 无候选 / Mimo 全部否决） | 输出提示"未检测到进球"，不崩溃，不生成空 mp4 |
| 候选片段重叠（两个时间戳间距 < 窗口宽度） | 合并为一个片段发给 Mimo，prompt 要求列出所有进球时间 |
| 临时文件管理 | 所有中间文件写入 `./.highlight_cache/`，脚本结束自动清理；加 `--keep-cache` 选项保留 |
| 视频文件过大（>300MB 或时长过长） | 启动时检查，超限则提示用户先压缩或降低分辨率 |
| 长时间无响应 | 添加 tqdm 进度条，每步有日志输出 |

### 核心风险

| 风险 | 缓解措施 |
|------|----------|
| **Mimo 不支持视频 base64 输入** | Step 0 首先验证；如不支持，备选方案为上传到临时文件服务获取公网 URL |
| **Mimo 无法返回时间戳** | 降级方案：只判断片段内"是否有进球"（是/否），时间戳用 CV 候选片段的原始时间戳代替 |
| Mimo 时间戳定位不准确 | Prompt 里要求返回"大约第几秒"，容忍 ±2 秒误差；用更宽的裁剪窗口补偿 |
| 固定机位下篮筐被遮挡 | ROI 手动标注（`--roi x,y,w,h`），选择篮筐下方网兜区域，遮挡概率较低 |
| 运动检测误报太多 | 二级时序模式过滤 + Mimo 精判兜底；Mimo 的误拒绝（false negative）是更需要关注的问题 |
| 视频文件过大（>300MB） | 录制时控制码率；或先用 ffmpeg 压缩到合理大小 |

## Open Questions

1. Mimo v2.5 视频理解能否返回带秒数的具体事件描述？需要写一个简单的测试脚本验证
2. 篮筐 ROI 是全自动检测还是让用户手动框选？初版建议手动标注
3. 进球前后的裁剪窗口多宽？（建议进球前 5 秒 + 进球后 3 秒）
4. 是否添加配乐/转场？初版建议 pure 拼接，不加花活

## Success Criteria

- 输入一段 15-30 分钟的半场 3V3 比赛视频（固定机位）
- CV 粗筛能覆盖 80%+ 的进球（高召回，精确度由 Mimo 保证）
- 输出一段包含大部分进球瞬间的集锦 mp4
- 一键运行：`python highlight.py game.mp4 -o highlights.mp4 --roi 640,120,200,300`
- 处理一场比赛的成本控制在 5 元以内（Mimo API 费用）

## Next Steps

### Step 0: 核心能力验证 — Go/No-Go 关口（最先做！）

写一个最小测试脚本 `test_mimo_video.py`，用一段 15-30 秒的篮球进球短视频，测试三个问题：

1. **接入方式**：Mimo v2.5 API 能否接受视频 base64 编码（格式 `data:video/mp4;base64,...`）？如不支持，公网 URL 方式是否可用？
2. **识别能力**：能否识别出"这是一个进球"？
3. **时间定位**：能否返回进球发生的具体秒数？（备选：只返回是/否）

**验证通过标准：** 至少能判断视频中"是否有进球"（是/否）。时间戳定位是加分项。
**如果验证失败：** 降级为纯 CV 路线——用更精细的运动检测 + 启发式规则（球穿过篮网的运动轨迹模式）来判断进球，不使用 VLM。这需要更多 CV 调参工作但仍然是可行的。
**如果验证通过：** 继续 Step 1。

### Step 1: 搭建视频处理骨架
- OpenCV 读取视频、计算帧间差分
- ffmpeg 裁剪和拼接的 subprocess 封装
- 命令行参数解析 (argparse)

### Step 2: 运动检测 + 候选片段生成
- 篮筐 ROI 定义（手动标注或配置文件）
- 帧间差分阈值调参
- 候选片段提取和临时保存

### Step 3: Mimo 判定集成
- 复用现有 `mimo_mcp_server.py` 的 API 调用模式
- 批量发送候选片段，收集判定结果
- 错误处理和重试

### Step 4: 集锦生成 + 调优
- ffmpeg 拼接所有确认片段
- 端到端测试，调优各环节参数
- 可选：进度条、日志输出
